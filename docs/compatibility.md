# Совместимость ModernUI

Этап 01, 2026-11-01. Статус по умолчанию — **не проверено**. Отметка меняется только по реальной
проверке с датой, стендом (чистый / dev) и ссылкой на запись в `verification.md`. Частные модули и
доработки конкретной CRM, входящие в обязательную матрицу dev-стенда, описаны в `PRIVATE.md`.

повторных проверок затронутых адаптеров по `visual-parity.md`. Прежнее «осталось как v7» не
оправдывает визуальное расхождение; fallback допустим для конкретной доказанной несовместимости.

## 3. Каталог событий ядра v7 (тег 8.4.0)

`app.event` — шина `jQuery({})` (`layouts/v7/resources/application.js:146–161`), не привязана к DOM:
перерисовка DOM не теряет подписчиков, но события перестают приходить, если перестают вызываться
функции контроллеров v7. Вторая группа — jQuery-события на элементах, они всплывают и требуют
прежних контейнеров. Опечатки в именах — часть API (`Vtiget.Dashboard.PostLoad`,
`Vtiger.Referece.Popup.Pre`, `…Messsage`).

Правила ModernUI:

1. Сохранение, загрузка, фильтрация, пагинация, inline-правка остаются в контроллерах v7
   (`Vtiger_List_Js`, `Vtiger_Detail_Js`, `Vtiger_Edit_Js`, `Inventory_Edit_Js`, `Vtiger_Index_Js`) —
   события выше возникают только там. ModernUI не переписывает эти потоки на Vue.
2. Контейнеры всплывающих событий сохраняются: `tr.listViewEntries[data-id]` внутри страницы списка,
   `.sourceField` внутри `td` поля, контейнеры виджетов, `li` фильтров.
3. Острова ModernUI подписываются на `app.event` только через адаптер (снятие подписок в `unmount`) и
   никогда не вызывают `app.event.off(name)` без своего обработчика.
4. Свои запросы ModernUI делает через `fetch`, а не `jQuery.ajax`: многие расширения висят на
   глобальном `ajaxComplete` и пересканируют страницу после каждого jQuery-запроса.

Особенности ядра 8.4.0, найденные на этапе 02 (влияют на любое расширение):

- `WebUI.php` не подключает csrf-magic для `mode=reset`, `mode=fromMig` и `action=Login`; POST
  расширения с такими параметрами падает на `validateWriteAccess()` (`csrf_check` не определена).
  ModernUI их не использует (`tests/php/RoutesTest.php`).
- `Header.tpl` выводит `<input id="inventoryModules">` внутри `<head>`: тема v7 и все HEADERCSS
  оказываются в начале `<body>` (до содержимого страницы).
- Скин v7 задаёт `.navbar-fixed-top { z-index: 1095 !important }`, `.modal` — 1100, `#overlayPage` — 1099:
  выпадающим элементам расширений нужен слой между 1095 и 1099.
- Подпись пункта «Настройки → Прочие» переводится модулем текущей страницы настроек: имя пункта лучше
  делать читаемым без перевода.
- `PearDatabase::fetch_array()`/`query_result()` HTML-кодируют значения; JSON из базы читается через
  `raw_query_result_rowdata()`.

Особенности чистой 8.4.0, найденные на этапе 03 (архив релиза, PHP 8.1 и 8.5; ModernUI их не исправляет —
обходит или учитывает):

- Git-тег `8.4.0` не содержит `vendor/`: установка из тега отвечает «Please install composer dependencies.»;
  архив релиза — тот же код с `vendor/` и более новым `composer.lock` (Smarty 4.5.5).
- CLI-скрипты должны подключать `vendor/autoload.php` (как `index.php`): иначе логгер падает на
  `Monolog\Logger`. `vtlib/tools/console.php` этого не делает и молча выходит с кодом 0 — обход
  `php -d auto_prepend_file=vendor/autoload.php …`; аргумент — `--remove=<Модуль>`.
- `config.php` для веб-запросов оставляет `error_reporting(E_ERROR…)`: предупреждения и deprecated видны только
  со штатным `config_override.dev.php` (копия в `config_override.php`, журнал `logs/phperr.log`).
- `vtws_create()` документов с товарными строками (SalesOrder и др.) падает «Id specified is incorrect»: события
  перед сохранением требуют id записи; ключ строк — `LineItems`. Форма редактирования работает.
- Первый вход администратора — мастер SystemSetup (выбор функций), первый вход каждого пользователя — UserSetup;
  его сохранение пересоздаёт файлы привилегий пользователя.
- После удаления модуля его файлы остаются, и менеджер модулей предлагает для ZIP только «Update Now», которое
  для незарегистрированного модуля падает («ZIP File is corrupted or empty»).
- В базе после установки есть `HEADERSCRIPT` на отсутствующие файлы (`ExtensionStore.js`, `ModCommentsCommon.js`,
  `SMSNotifierCommon.js`) — `Header.php` их пропускает; `bootstrap-legacy` ссылается на отсутствующий
  `glyphicons-halflings.png` (404).
- Исходные предупреждения ядра на экранах baseline: `modules/Inventory/models/Record.php` (форма заказа),
  `LineItemsDetail.tpl` (`subprod_names`), `modules/Calendar/actions/Feed.php`, `include/utils/UserInfoUtil.php`;
  на PHP 8.5 дополнительно «Cannot use string as array» в `Settings_Vtiger_Module_Model::getInstance()` на каждой
  странице настроек (включая страницу ModernUI — она наследует `Settings_Vtiger_Index_View`), deprecated в
  `ExtensionStore/libraries/RestClient.php`, `GuardedArray.php`, `Services.php`, `VtigerLineItemOperation.php`.
- Установщик отправляет регистрацию на сервер вендора и показывает пиксель статистики; на чистом стенде сеть
  закрыта, запрос браузера блокируется.

## 4. Отличия модифицированных сборок 8.4

На dev-стенде ядро v7 не стоковое (сборка на основе SalesPlatform и правки установки). Из
обнаруженного важно для темы:

- `Header.php` может пропускать ресурсы отключённых модулей; `Link.php` сортирует ссылки по
  `sequence`; `PackageImport::import_CustomLinks()` исправлен. ModernUI ни на что из этого не опирается.
- Шаблоны v7 изменены: сетка `ModuleHeader.tpl`, меню «Ещё» в `DetailViewActions.tpl` заменено
  встроенной группой кнопок, `Pagination.tpl`, `Topbar.tpl` (дополнительная разметка с inline-стилями
  у логотипа), `SidebarEssentials.tpl`, скрытое поле `input[name=locale]` в `Header.tpl` и
  дополнительные библиотеки (pnotify, visibility, inputmask) в `JSResources.tpl`/`Basic.php`.
- JS ядра изменён: `Vtiger.js`, `Detail.js`, `Edit.js` (второй путь сохранения с теми же событиями
  `PreAjaxSaveEvent`/`PostAjaxSaveEvent`/`post.save.failed`, собственные оверлеи на `body`),
  `Popup.js` (оконные popup v6), `Utils.js`, `validation.js`.
- Модули Inventory и некоторые другие используют собственные копии `ListViewContents.tpl` эпохи 7.x.
- CSS ядра и библиотек местами задан с `!important` или inline (этап 10, `design.md` §13.5): `select2-bootstrap.css` сборки
  (SalesPlatform) красит подсвеченный пункт `#337ab7 !important`, скин v7 — ссылки `.fieldValue .value a` `#1155cc !important`,
  `uitypes/Boolean.tpl` — флажок формы `style="width:15px;height:15px"`, белая подложка модальных окон. Облачные значения темы для
  этих ролей заданы с `!important` только в узких селекторах (строки и ссылки с inline-цветом расширений исключены селектором);
  на чистой 8.4.0 те же правила дают тот же результат (сценарий `foundation` на обоих стендах).

Следствие: skin пишется по устойчивым классам (`.listViewEntries`, `.fieldLabel`, `.fieldValue`,
`.detailview-header`, `.btn`, `.modal`) с нейтральной обработкой незнакомой разметки, а не по
точной DOM стоковых шаблонов; тема не переопределяет шаблоны ядра (`Viewer` и не позволил бы
сделать это без копий). Конкретный список изменённых файлов dev-стенда — `PRIVATE.md`.

### 5.5. Глобальные стили расширений

VTExperts Module & Link Creator (`.alert-warning`), VTExperts Customer Feedback (`.bold`,
`.margin-bottom-20`, `.fa-star:hover`), vtDigiSign (`.signature`), CT* (inline `<style>` для
`.nav-tabs`) переопределяют общие классы глобально. Skin не воюет с ними `!important`; специфичность
skin выше за счёт `:root:not(.mu-off)`, поэтому визуальный результат на экранах с такими модулями
проверяется отдельно.

### 5.6. Общие наблюдения

- Скрипты расширений читают `_META` (`Header.tpl`) через `app.getModuleName()/getViewName()` и
  `app.getRecordId()` (`#EditView [name=record]`, `#recordId`). Тема не меняет `_META`, `#recordId`,
  `#EditView`, `#detailView`.
- HEADERSCRIPT расширений грузятся после базовых скриптов v7 и до `Vtiger.js`/скриптов view; порядок
  подключения тема не меняет.
- Некоторые расширения устанавливают свои копии шаблонов в каталоги ядра (`Users/Login.tpl`,
  `Vtiger/uitypes/*`) — тема не переопределяет шаблоны, поэтому конфликтов файлов нет.
- `MutationObserver` и `DOMNodeInserted` расширения не используют; пересканирование по
  `ajaxComplete` — частое.

## 6. Адаптеры: переносимые и специфичные

| Вид | Где живёт | Пример |
|---|---|---|
| Базовое поведение для ядра v7 | ZIP, `frontend/src/adapters/v7/` | шапка, меню приложений, модалки, Select2, списки, формы |
| Переносимый адаптер публичного расширения | ZIP, `frontend/src/adapters/ext/<Расширение>/`, включается при `vtlib_isModuleActive(<модуль>)` (список приходит в `Bootstrap`) | выравнивание кнопок PDFMaker в заголовке карточки; правило для строк Listview Colors |
| Специфичный адаптер конкретной CRM | вне базового ZIP: отдельный необязательный профиль (этап 08), описание — `PRIVATE.md` | собственные модули и поля заказчика |

Адаптер — это CSS и наблюдатели, не правка чужого кода и не копия чужих файлов. Адаптер
расширения не включается, если модуль не активен.

Реализовано на этапе 08 (`architecture.md` §7.6): реестр `ModernUI_Adapters_Model` проверяет наличие и активность модуля, версию
(проверенный диапазон), файлы и таблицы расширения и выключатель администратора («Совместимость» редактора, ключ `adapters.disabled`);
стили адаптера приходят только в таблице токенов пользователя с активным расширением, клиентская часть — отдельным chunk с проверкой
DOM, правила экранов `skin`/`standard`. Отсутствие модуля, неподходящая версия, недостающий файл или таблица дают общий skin, сбой
проверки — все адаптеры выключены на запрос, страница работает. В 0.6.0 один адаптер — `pdfmaker` (PDF Maker 4.x). Специфичное для
конкретной CRM (скрытие модулей в меню отдельной роли и т. п.) — профиль настроек ModernUI этой CRM (JSON для «Импорт и экспорт»),
который хранится вне репозитория; кода её адаптеров в пакете нет.

## 7. Известные ограничения (на 2026-11-01, дополнено на этапе 08)

- Этап 08: адаптеры есть только для проверенных расширений и версий; новая версия расширения вне диапазона адаптера получает общий
  skin, пока адаптер не проверен с ней. Совместимость с любым неизвестным кодом не обещается: неизвестный экран получает общий skin
  (или только стили, если его оболочка не похожа на v7), администратор может перевести его в стандартный вид исключением экрана.
- Этап 08: страница импорта, открытая по прямому адресу (`view=Import` без оверлея списка), падает в самом v7 (контроллер страницы не
  найден) — тема стартует оболочку после `load` и не исправляет сам экран.
- Этап 08: в правке веб-формы кнопка «Сохранить последовательность» выходит за правый край и в v7 (прокрутка 33 px); с темой кнопка
  шире на 8 px.
- Этап 08: переключатели и полосы шагов мастеров — разметка и вид v7 (цвет акцента вместо зелёного у включённого переключателя).
- Этап 08: отключённая основная кнопка темы — заливка акцента с непрозрачностью 0,65 (у v7 — бледно-зелёная); состояние читается по
  курсору и `disabled`, а не по цвету (например, пакетный экспорт PDF Maker до выбора шаблона).
- Этап 08: на чистой 8.4.0 под PHP 8.5 ядро отвечает «Failed to parse time string ( )» на быстрое создание события из календаря
  (событие при этом сохраняется) и обрывает своим окном ошибки полные формы события и задачи (`module=Events|Calendar&view=Edit`) — и без
  темы; на таких страницах нет объекта `app` v7, тема даёт только стили. На PHP 8.1 формы работают.
- Этап 08: на dev-стенде страница входа v7, открытая уже вошедшим пользователем (`module=Users&view=Login`), падает в шаблоне шапки
  самой сборки — тема там не участвует (страница входа не получает ресурсов темы).


- `HEADERLINK` (ссылки шапки vtlib) layout v7 не выводит вообще (`Vtiger_Header_View::getHeaderLinks()` используют только
  шаблоны устаревшего `vlayout`): тема их тоже не показывает. На dev-стенде таких ссылок нет (этап 06).
- На ширине < 768 px строки шапки v7 начинаются на 20 px левее окна (и без темы): «гамбургер» и логотип v7 частично срезаны.
  Кнопка мега-меню темы сдвигается в окно, полоса избранного привязана к окну.
- Меню приложений v7 со своей кнопкой расширения (элемент без ссылки) не скрывается: рядом остаётся кнопка мега-меню темы
  (этап 06, `architecture.md` §7.1).

- Экраны расширений со своей копией оболочки получают только skin; shell (навигация темы) на них
  может не появиться — допустимо, функционал сохраняется.
- Немецкий/русский интерфейс ядра и расширений появляется только при установленных языковых пакетах
  CRM; тексты самой темы переводятся всегда (`I18N.md`).
- Вход в CRM (`Users_Login_View`) не получает HEADERSCRIPT/HEADERCSS — страница входа не оформляется.
- Модальные окна v7 (быстрое создание и др.) сохраняют геометрию v7 (поля 30 px, шапка ≈ 51 px): v7 рассчитывает
  высоту тела окна под свои размеры. На сборках, где у тела быстрого создания есть `max-height` без
  mCustomScrollbar, тема добавляет телу прокрутку, иначе длинная форма перекрывала подвал (этап 04).
- Связанные вкладки карточки v7 имеют фиксированную ширину (90 px): тема держит подписи 12 px с весом 500 (как v7 по ширине);
  длинные подписи соседних вкладок могут соприкасаться так же, как без темы (этап 07: не больше, чем у v7).
- Открытая inline-правка, которую не сохранили и не отменили, v7 сохраняет при уходе со страницы (и без темы); после отказа
  сервера значение остаётся в поле правки (этап 07, сценарий `records`).
- v7 отправляет комментарий как `FormData` всей формы карточки: в запросе есть и поля блоков правки уже существующих комментариев
  (так и без темы).

## 9. Запись поверх списка (этап 09, 2026-11-07)

Новая компоновка (`architecture.md` A15, §7.7) опирается на overlay-виды ядра 8.4 и их события, поэтому расширения видят
запись и форму так же, как в связанных списках карточки v7:

- `post.overlay.load` (после показа записи) и `post.overLayEditView.loaded` (после показа формы) — те же события, что вызывает
  `Detail.js`; Conditional Layouts (ControlLayoutFields) и подобные, подписанные на них, работают на форме поверх списка.
- Содержимое запрашивается `app.request` (jQuery): обработчики `ajaxComplete` расширений срабатывают как после любого
  AJAX-запроса v7. Найдено на dev-стенде: подписчик одного из расширений на `post.overLayEditView.loaded` добавляется заново на
  каждый `ajaxComplete` (+1 за запрос) — так же копится и без темы при работе со списком; на чистой 8.4 рост 0.
- Отправка формы проходит валидацию и `Vtiger_Edit_Js.recordPresaveEvent` v7 и расширений; ModernUI перехватывает уже
  навигацию отправки — и событием `submit`, и `form.submit()` расширения (так отправляет форму изменённая сборка dev-стенда) — и
  отправляет тот же `FormData`. Индикатор «Сохранение», который изменённые сборки показывают до ухода со страницы, скрывается
  штатным `app.helper.hideProgress()`.
- Скрипты расширений, стартующие только по `ready` при `_META.view == 'Detail'/'Edit'` (кнопки PDF в заголовке карточки,
  автодополнение адреса в полной форме и т. п.), на записи поверх списка не запускаются — их действия доступны на полной
  странице записи (кнопка «(Просмотр)/Details» окна, один щелчок). Перенос действий в окно — этап 13; модуль, которому они
  нужны в окне, не включается в `layout.modules`.
- v7 копит обработчики при каждом показе модалки (`focusin.modal` своего `enforceFocus`) и старте формы (кнопки
  `.modal .close/.cancelLink`); ModernUI снимает добавленное при уходе вида записи — на странице, открытой долго, ничего не
  накапливается (проверено `layout`).

### Списки и PDFMaker (этап 12)

Перекомпоновка списков применяется в виде `List` по наличию стандартного контейнера и `.listViewActionsContainer`,
включая изменённые шаблоны inventory. Таблица должна находиться вне контейнера действий: иначе его нельзя
перенести в полосу инструментов. Одинаковый контракт проверяется в CSS до запуска JS и в адаптере.
Панель фильтров, ссылки расширений, колонковый поиск, теги,
selected/excluded ID, сортировка, page size и пагинация остаются штатными. Дополнительные счётчики
сохраняют числа и URL, их цвет становится акцентом карточки; цветные строки не перекрашиваются.

Адаптер PDF Maker 4.x дополнен клиентской частью: отдельная кнопка массового экспорта существует
только при штатной доступной ссылке PDFMaker. Она вызывает оригинальный обработчик. Шаблоны,
язык, права и документы остаются за расширением. Проверяется реальный пакетный PDF по двум
синтетическим заказам против v7; также отсутствие кнопки без выбранных строк, диалог без выбранного
шаблона и узкий экран. На чистой CRM без коммерческого расширения адаптер не загружается.

Специальные списки без этого контракта (корзина со своей полосой действий, таблица внутри контейнера
действий расширения, список внутри другого вида страницы) не получают
адаптер обычного списка. Их действия и поиск проверяются инвентарным аудитом; облачная переработка
специальных экранов относится к этапу 17.

### Карточки поверх списков (этап 13)

Карта интеграции: `adapters/v7/record.ts` — native Detail, метаданные, JS/CSS и жизненный цикл;
`record/presentation.ts` — оболочка и поиск разрешённых полей; `adapters/ext/pdfmaker/index.ts` —
инициализация публичного контроллера PDF Maker при `post.overlay.load`, поскольку его ready-handler
на исходной странице видит List. Шаблоны, права, скачивание и подпись принадлежат расширению.
Native actions остаются в доступном меню, а не удаляются ради компактной шапки.
Две кнопки PDF Maker остаются рядом с меню действий; его native dropdown сохраняет шаблоны и язык.

Связанные строки Detail/Edit открываются отдельной вкладкой по исходному URL (§7.10 архитектуры).
Это сохраняет родительскую карточку при единственном overlay-контейнере ядра. Таблицы, создание,
выбор связи, удаление связи, поиск и пагинация исполняют штатные обработчики. Сторонние классы
Detail и зависимости подключаются динамически; ошибка запуска ведёт к прямой карточке.
Совместимость неизвестного расширения с произвольными глобальными ready-handler не заявляется.

Набор виджетов, полей и действий определяется Open Source и установленными расширениями. Cloud AI,
Analytics и отсутствующие виджеты не имитируются. Отдельный экспорт/подпись проверяется только там,
где соответствующий модуль установлен; чистая установка не получает коммерческий код.
Фактическая проверка PDF включает скачивание и сравнение текста документов; юридическое подписание
и отправка третьим лицам в сценариях не выполняются. Наличие и доступность исходных handlers подписи
не означает проверку внешнего сервиса подписи.

### Формы и поля расширений (этап 14)

Create/Edit/Duplicate используют настоящий Edit view модуля с его серверными правами,
контекстом возврата, uitype и событиями. Библиотеки, объявленные внутри шаблона поля (например,
поле подписи), загружаются перед inline-инициализацией так же, как зависимости заголовка.
Общие jQuery/Bootstrap/Select2/Vue не заменяются. Quick Create остаётся штатным AJAX-сценарием.

Conditional Layouts, Advanced Custom Fields, Field Autofill, динамические и связанные блоки
сохраняют исходные таблицы, IDs/name, hidden/required/readonly и обработчики. Vue получает только
собственную навигацию. Поиск не раскрывает скрытые поля и не исключает обязательное поле из
native validation. Inventory использует вычисления и row handlers установленной CRM; тема
не исправляет отличия её серверных итогов от клиентских. Они сравниваются с её же режимом OFF.

### Системные настройки (этап 15)

Каталог главной настроек — штатное меню настроек текущей CRM: в нём ровно те пункты, которые сервер
печатает администратору, включая пункты установленных расширений (VTE, IT-Solutions4You, SalesPlatform и др.)
с их переводами и адресами. Скрытые и недоступные настройки не появляются; поиск работает только по ним.
Сводка — штатные числа 8.4 (активные пользователи, активные обработчики, модули); облачные лимиты и
хранилище не изображаются. Пины и перетаскивание пунктов в ярлыки v7 сохранены.

Страницы расширений в каркасе настроек получают общие правила семейства (шрифт, кнопки, таблицы, вкладки,
диалоги); их разметка, скрипты и окна не меняются. Страница, у которой нет боковой навигации настроек v7,
остаётся в обычном оформлении темы. Обязательная матрица dev-стенда: каждый пункт меню настроек
(66 экранов, в том числе расширений) сравнён с той же CRM без темы — действия, ошибки, прокрутка.

Штатные особенности 8.4, которые тема не исправляет: редактор списков записывает подписи новых значений в
`languages/<язык>/custom/<Модуль>.php` и не удаляет их вместе со значением; удаление пользователя —
подтверждение и диалог переноса записей с флажком постоянного удаления; маленькие значки панели узла
дерева ролей v7 не проходят проверку попадания указателя Playwright и в v7 (сценарий вызывает ссылку как
ссылку). Ниже 992 px боковая навигация настроек скрыта, как в v7.

### Остальные экраны и расширения (этап 17)

Особые экраны ядра получили облачную компоновку (`design.md` §13.13, `architecture.md` §7.14) над теми же узлами и обработчиками
v7. Для расширений это значит:

- **Цвета.** Цвет календаря (тип событий, пользователь, группа) читается из inline-цвета строки, который ставит сервер или
  `Calendar_Calendar_Js`, и рисуется флажком этого календаря; цвета событий, приоритетов задач, строк отчётов и списков
  (VTE Listview Colors) не перекрашиваются. Запрос раскраски строк Listview Colors после смены папки отчётов уходит так же, как без
  темы (`special-screens`).
- **Списки ядра со своими шаблонами** (отчёты, корзина, шаблоны писем) — в контракте списка этапа 12 по разметке ядра. Расширение
  с похожей вложенной разметкой (таблица внутри полосы действий, как VReports) этот вариант не получает и остаётся со своей
  компоновкой — без предположений о его структуре.
- **Окна `fc-overlay-modal`** (импорт, экспорт, массовое изменение, слияние) — окно облака вокруг исходной разметки; шаги, поля,
  загрузка и кнопки — v7. Окна записи/форм этапов 13–14 и страницы настроек не затрагиваются. Неизвестное расширение, которое
  открывает свой оверлей с этим классом, получает только рамку окна и порядок кнопок подвала.
- **Неизвестный модуль** (Gadgets, Gizmos на чистом стенде): список в компоновке этапа 12, карточки и формы 13–14, меню и права —
  как раньше (`clean`, `special-screens`); экраны, которые v7 обрывает своей ошибкой, получают только стили (`skin`).
- Отключение: администратор переводит любой экран в стандартный вид исключением экрана; «Стандартный вид» и сбой shell возвращают
  исходную компоновку всех семейств этапа.

## 11. Браузеры (этап 19, ModernUI 0.17.0)

Поддерживаемый диапазон определяется `:has()`, на котором стоят skin и острова: **Chrome/Edge ≥ 105, Firefox ≥ 121,
Safari ≥ 15.4**; цель сборки CSS равна этому минимуму (`dependencies.md` §8), JS — ES2020. Более старый браузер получает
стандартный вид v7 по частям правил — такая конфигурация не поддерживается и не проверялась.

Проверено на чистом стенде PHP 8.1 и PHP 8.5 сценарием `test:browsers` (Playwright 1.63):

| Движок | Версия | Результат |
|---|---|---|
| Chromium | 153.0.8010.12 (build 1243, принятые снимки) | PASS: шапка 96 px, Poppins загружен из CRM, основной `#3978fe`, нет полосы модулей; мега-меню мышью и клавиатурой (Escape возвращает фокус); окно записи, Escape, Back/Forward, правка и отмена в окне; редактор ModernUI и вкладки, серверная форма, предпочтения; безопасный режим; отказ `Bootstrap` → рабочий v7 без перекрытия первой записи |

Различия: `document.fonts.check()` без текста в Firefox учитывает и незагруженные подмножества шрифта (проверка идёт по
фактически загруженным начертаниям); WebKit выводит имена семейств без кавычек. Других различий вида и поведения в этих
сценариях нет. Ошибок скриптов темы ни в одном движке нет. До 0.17.0 Chromium и WebKit применяли дубли правил
`:-webkit-any()`, которых Firefox не понимает; теперь каскад у всех трёх одинаков. Визуальные baseline сняты только в
Chromium 1243; смена браузера принятых снимков требует пересмотра (`visual-acceptance.md`).
