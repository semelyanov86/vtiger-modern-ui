# ModernUI 01 — Окружение, имя модуля и архитектура

Рабочий каталог: корень этого репозитория. Прочитай `PRIVATE.md` (если есть), `AGENTS.md`,
`docs/COMMON.md`, `docs/PLAN.md`, `docs/DEVELOPMENT.md`, `docs/I18N.md` и `docs/RESEARCH.md`.
Общие требования обязательны.
Предусловие: подготовка (этап 00) выполнена — репозиторий, документы, `task crm:link`.
Если этап уже начат, продолжи по журналу.

## Сначала проверь окружение

1. Репозиторий: `git rev-parse --git-dir --git-common-dir` — собственный `.git`, remote нет, в истории
   и рабочем дереве нет кода CRM, `.env`, vendor, дампов, коммерческих модулей; `task privacy` чист.
2. dev-стенд: `task crm:status` и `task crm:smoke`. Зафиксируй версию Vtiger, ветку и SHA CRM
   (в `PRIVATE.md`), доступность адреса, состояние путей ModernUI, отсутствие регистрации модуля.
   Если стенд не отвечает — действуй по `PRIVATE.md`; CRM не чини.
3. Имя модуля: проверь `ModernUI` в базе стенда (`vtiger_tab`, `vtiger_links`, `vtiger_settings_field`),
   в его каталогах, в официальном теге `8.4.0`, по доступным сведениям о расширениях Vtiger Marketplace.
   При конфликте переименуй последовательно до появления пакета: документы, `dev/crm-mounts.txt`,
   `MU_MODULE` в `.env.example`, решение — в журнал.

## Задача

Спроектируй отдельный устанавливаемый модуль ModernUI для Vtiger Open Source 8.4. Результат всей
последовательности — рабочий интерфейс по образцу облачного Vtiger, Vue 3 + Vite, настройки
темы/меню, RU/EN/DE, сохранение расширений и быстрая проверка на dev-стенде. На этом этапе —
проверенная спецификация, без регистрации модуля в базе стенда.

## Выполни

1. Сравни точки расширения CRM dev-стенда и официального тега 8.4.0: глобальные ресурсы, link handlers,
   права, lifecycle, менеджер модулей, manifest, пути распаковки, настройки, языки, меню, AJAX/PJAX.
   Для каждого выбранного механизма приведи файл и фактический порядок вызовов. Не полагайся на
   изменения ядра конкретной установки (`RESEARCH.md`: `isLinkOfInactiveModule`, сортировка ссылок).
2. Через Playwriter уточни визуальный образец (экземпляр — в `PRIVATE.md`): меню, список, карточка,
   форма, popup. Не копируй коммерческие исходники. Составь design.md: размеры, палитра, шрифты с
   кириллицей и ä/ö/ü/ß, плотность, состояния, экранные критерии. Если облако недоступно, используй
   `RESEARCH.md` и доступные снимки, явно обозначив пределы.
3. architecture.md: extension-модуль без entity-таблиц клиентов, собственные настройки, Vue-контейнеры,
   адаптер к v7, серверные действия, CSS-изоляция, загрузчик для `text/javascript` HEADERSCRIPT,
   базовый URL (в т. ч. подкаталог), жизненный цикл, восстановление, границы ответственности DOM.
   Отдельно — как сохраняются кнопки, вставленные расширениями в шапку и формы.
4. Выбери одну Vue-библиотеку компонентов или обоснуй минимальный собственный набор: официальные
   источники, лицензия, CSS-изоляция от Bootstrap 3, доступность, RU/EN/DE locale, размер сборки.
   Запиши в dependencies.md.
5. settings.md: общие/ролевые/личные настройки, точный приоритет, схема JSON, версия схемы и
   миграции, предпросмотр, конфликты сохранения, перенос между экземплярами, default/disable/update/
   uninstall. Меню формируется из разрешённых модулей текущего пользователя.
6. compatibility.md: чистая 8.4, dev-стенд, PHP 8.1/8.5, MySQL, RU/EN/DE, роли, типы экранов, публичные
   сторонние расширения. По умолчанию — «не проверено». Найди DOM-зависимости критических модулей
   (`RESEARCH.md` — начало реестра; обязательная матрица dev-стенда — `PRIVATE.md`). Отдели переносимые
   адаптеры от специфичных для конкретной CRM (последние описываются в `PRIVATE.md`).
7. Структура репозитория: `src/` (раскладка путей CRM, как в `DEVELOPMENT.md`), `frontend/`,
   `packaging/`, `dev/`, `tests/`, `dist/`; собственные миграции, словари, mapping `src/` → ZIP
   (`settings/…` для `modules/Settings/ModernUI`). Сверь с `vtlib/Vtiger/PackageImport.php` тега 8.4.0.
   Если структура отличается от `dev/crm-mounts.txt`, исправь карту и проверь `task crm:status`.
   Опиши, куда сборка Vite пишет результат внутри подключённого каталога, и план команд этапа 02
   (`build`, `dev`/watch, `package`, `crm:install`, `crm:update`, тесты).
8. Спроектируй чистый стенд для этапа 03 (Docker-проект темы, образы, источник 8.4.0, PHP 8.1 и по
   возможности 8.5, свой адрес) и PACKAGE-прогон на dev-стенде.
9. Составь матрицу приёмки: действие → ожидаемый результат → роль → стенд (чистый / dev) → способ
   проверки. Обязательно: сохранение форм, права, настройки меню, lifecycle, три языка, правка →
   видимый результат на dev-стенде, отсутствие изменений в git CRM.

## Готовность

- Окружение проверено, версия стенда зафиксирована, имя модуля свободно или последовательно заменено.
- Есть конкретный реализуемый путь установки без патчей ядра, схема ресурсов и пакета.
- Схема DEV (подключение к dev-стенду, регистрация lifecycle) и PACKAGE (чистый стенд, dev-стенд без
  подключения) описана до уровня команд.
- RU/EN/DE включены в архитектуру и проверки с первого этапа.
- Настройки и меню описаны до уровня проверяемого поведения, включая права и перенос.
- Неопределённости проверены по коду или оформлены как конкретные проверки этапов 02–03.
- Если обязательное требование невозможно без патча ядра, не скрывай это за словом «модуль»: найди
  способ через доступные расширения; без решения архитектура не завершена.
