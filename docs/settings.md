# Настройки темы и меню

Этап 01, 2026-11-01. Спецификация поведения, которое реализуют этапы 02 (схема, миграции, lifecycle)
и 05 (интерфейс настроек и меню). Архитектура — `architecture.md`, языки — `I18N.md`. Фактическое поведение
этапа 05 (2026-11-04) — в абзацах «Реализовано на этапе 05» и §13.

## 1. Области и кто их меняет

| Область | Ключ области | Кто меняет | Где |
|---|---|---|---|
| `default` | — | код пакета (константы, версия схемы) | `ModernUI_Settings::defaults()` |
| `global` | `''` | администратор | Настройки → ModernUI |
| `role` | `roleid` роли Vtiger | администратор | Настройки → ModernUI → вкладка «Роли» |
| `user` | `id` пользователя **из сессии** | сам пользователь (только разрешённые ключи); администратор может только сбросить | Предпочтения темы |

Пользователь Vtiger имеет ровно одну роль (`vtiger_user2role`). Настройки роли наследуются
подчинёнными ролями только при флаге `inherit: true` у ролевой записи (по умолчанию нет); выбирается
ближайшая роль вверх по `parentrole`, у которой есть запись с `inherit: true`, если у собственной
роли записи нет.

## 2. Приоритет

Для каждого ключа: `default` → `global` → `role` → `user`; более поздняя область перекрывает
предыдущую, **только если ключ разрешён в этой области** (таблица §4). Значение `null` или
отсутствие ключа означает «не задано, взять из предыдущей области». Неизвестные и невалидные
значения при чтении отбрасываются (с предупреждением администратору), а не ломают слияние.

Составные значения:

- `navigation.groups` и `navigation.hidden` — заменяются целиком областью `role`, если в ней заданы
  (слияние двух деревьев меню непредсказуемо для администратора);
- `theme.excludedScreens` — объединение `global` и `role`;
- `navigation.favorites` — только `user`.

## 3. Включение темы

`theme.mode` (только `global`): `off` | `pilot` | `all`. После первой установки — `off`.

| `theme.mode` | Тема активна для пользователя, если |
|---|---|
| `off` | никогда |
| `pilot` | пользователь в `theme.pilot.users`, или его роль в `theme.pilot.roles` (с подчинёнными при `includeSubordinates`), и он не выбрал «Стандартный вид»; либо `theme.allowSelfEnable` и пользователь сам включил тему (`user.selfEnabled`) |
| `all` | пользователь не выбрал «Стандартный вид» (если `theme.allowOptOut`) |

Дополнительно тема не активна, если: модуль выключен, версия Vtiger не 8.4.*, версия схемы БД не
равна версии кода, в сессии безопасный режим (`modernui=off`), текущий экран в
`theme.excludedScreens`, нет production-сборки. Решение принимает `ModernUI_LinkHandler`
(`architecture.md` §3.2) на каждой полной странице.

Кнопка «Включить для меня» на странице настроек: при `off` переводит в `pilot` и добавляет текущего
администратора в `pilot.users`; при `pilot` — только добавляет. Так выполняется требование «сначала
администратор для себя, затем для остальных».

Раздел «Пилотные пользователи и роли» той же страницы (этап 03, HTML-формы без Vue, POST с CSRF, только
администратор): списки `pilot.users` и `pilot.roles` с кнопками «Убрать», выбор активного пользователя или роли
(кроме корневой `H1`) и «Добавить». Принимаются только существующие активные пользователи и существующие роли;
добавление при `off` переводит режим в `pilot` (как «Включить для меня»), удалённый пользователь остаётся в списке по
id, чтобы его можно было убрать. Раздел скрыт при `theme.mode = all`. Полный редактор пользователей и ролей —
этап 05; формы остаются как путь без JavaScript.

Исключения экранов: `{ module, view, parent }`, каждое поле — имя (`^[A-Za-z0-9_]{1,50}$`) или `*`.
Сопоставляется с параметрами запроса полной страницы. Пример: `{ "module": "Reports", "view": "*",
"parent": "" }` — отчёты всегда в стандартном виде.

**Реализовано на этапе 05** (`ModernUI_Settings_Model::spec()`):

- `branding.logo` — `company` или `modernui_<sha1>.png`: загруженный файл всегда перекодируется в PNG (GD), имя
  выбирает сервер (§13.3); JPEG и GIF принимаются на входе, хранятся как PNG.
- `branding.title` — `company` (названия темы нет, в шапке остаётся логотип CRM, как без темы) или карта подписей.
  Название организации из «Сведения о компании» редактор только показывает рядом с вариантом «как в CRM».
- `navigation.groups` — список групп §6.1 (сам массив, без обёртки `{groups, hidden}`); `navigation.hidden` — отдельный
  ключ (≤ 500 имён модулей).
- Подписи (`label`, `branding.title`): варианты `ru-RU`, `en-US`, `de-DE`, `*`; управляющие символы и разделители
  строк заменяются пробелом, повторные пробелы сжимаются, длина 1–60 **символов** (не байт); отвергаются `<`, `>`,
  `javascript:`, `vbscript:`, `data:text/html` — ошибка с путём поля (`navigation.groups[0].label.de-DE`). Пустые
  варианты удаляются; у пункта-маршрута нужен хотя бы один вариант.
- Значки групп и пунктов — 66 имён Lucide (`ModernUI_Settings_Model::$menuIcons`, `frontend/src/menu/icons.ts`, общая
  фикстура `tests/fixtures/menu-icons.json`).
- Неизвестный ключ (`MU_UNKNOWN_KEY`) и неизвестное поле внутри меню (`url`, `href`, параметр маршрута вне
  `app/viewname/mode/parent`) отвергаются целиком, а не отбрасываются молча.

Запрещено хранить: произвольный HTML/JS/PHP, CSS-код, URL вне CRM, секреты, данные записей CRM.
Подписи — простой текст (выводятся как текст, `\p{Cc}` удаляются, длина 1–60 после обрезки).

## 5. Хранение, версия схемы, миграции

Таблицы (создаёт миграция `0001`, `ENGINE=InnoDB`, кодировка и collation — как у базы:
`SELECT @@character_set_database, @@collation_database`, по умолчанию `utf8mb4`/`utf8mb4_general_ci`):

```sql
vtiger_modernui_meta(name VARCHAR(64) PRIMARY KEY, value TEXT NOT NULL)
-- schema_version, installed_version, last_migration_at, last_error

vtiger_modernui_settings(
  id INT AUTO_INCREMENT PRIMARY KEY,
  scope VARCHAR(8) NOT NULL,              -- global | role | user
  scope_key VARCHAR(64) NOT NULL DEFAULT '',
  data MEDIUMTEXT NOT NULL,               -- JSON документа области, {"v":1,...}
  doc_version SMALLINT NOT NULL,          -- версия формата документа
  revision INT NOT NULL DEFAULT 1,        -- оптимистическая блокировка
  updated_by INT NULL, updated_at DATETIME NOT NULL,
  UNIQUE KEY uq_scope (scope, scope_key)
)
```

Установщик чистой 8.4.0 создаёт базу `utf8`/`utf8_general_ci` (`modules/Install/models/Utils.php:391`),
dev-стенд — `utf8mb4`. Поэтому `data` пишется `json_encode()` **без** `JSON_UNESCAPED_UNICODE`:
кириллица, умляуты и любые символы хранятся как `\uXXXX`, документ — чистый ASCII и не зависит от
кодировки таблицы; `scope_key` — ASCII по определению.

Миграции — `modules/ModernUI/migrations/NNNN_<name>.php`, класс `ModernUI_Migration_NNNN` с методом
`up(PearDatabase $db)`:

- идемпотентны: `CREATE TABLE IF NOT EXISTS`, проверка колонок/индексов через
  `information_schema` перед `ALTER`, преобразования документов только для строк с меньшим
  `doc_version`;
- меняют только таблицы `vtiger_modernui_*` и собственные регистрации (ссылки, пункт настроек);
- запускаются lifecycle (`postinstall`, `postupdate`, `enabled`) и действием `Recovery`;
- раннер берёт `GET_LOCK('modernui_migrate', 10)`, выполняет недостающие по порядку, после каждой
  успешной пишет `schema_version`; при исключении останавливается, пишет `last_error`, тема
  перестаёт подключаться до успешного повтора;
- откат версии не поддерживается: если схема БД новее кода (установлен старый ZIP), тема не
  подключается, страница настроек показывает «Схема настроек новее установленного модуля»;
- документ области хранит `v`; конвертеры `ModernUI_SettingsUpgrade` поднимают старые документы
  и используются также при импорте JSON старых версий.

## 6. Меню

### 6.1. Модель конфигурации

```json
{
  "groups": [
    {
      "id": "sales",                       // ^[a-z0-9_-]{1,32}$, уникален
      "source": { "app": "SALES" },         // необязательно: группа соответствует приложению v7
      "label": { "ru-RU": "Продажи", "en-US": "Sales", "de-DE": "Vertrieb", "*": null },
      "icon": "briefcase",                  // из разрешённого набора значков
      "collapsed": false,
      "items": [
        { "type": "module", "module": "Leads", "label": null, "icon": null },
        { "type": "route", "id": "my_calls", "label": { "ru-RU": "Мои звонки", "en-US": "My calls", "de-DE": "Meine Anrufe" },
          "icon": "phone", "route": { "module": "Calendar", "view": "List", "params": { "viewname": "12" } } }
      ]
    }
  ],
  "hidden": ["ModComments"]
}
```

Ограничения: ≤ 30 групп, ≤ 100 пунктов в группе, ≤ 1 уровень вложенности (группа → пункты).
`route`: `module`/`view` по `^[A-Za-z0-9_]{1,50}$`, `params` — только ключи `app`, `viewname`,
`mode`, `parent` с значениями `^[A-Za-z0-9_:-]{1,64}$`; ссылка строится сервером как
`index.php?module=…&view=…&…`. Внешние URL и `javascript:` невозможны по конструкции.
`route.params.viewname` (id фильтра) непереносим между CRM — при импорте пункт помечается
«проверьте фильтр».

### 6.2. Итоговое меню пользователя (сервер, `ModernUI_Menu`)

1. Кандидаты `C`: модули с `presence IN (0,2)`, для которых пользователь проходит
   `isAdminUser() || hasGlobalReadPermission() || hasModulePermission(tabid)` — из
   `Settings_MenuEditor_Module_Model::getAllVisibleModules()` (приложения v7) и активных
   entity-модулей с представлением списка; плюс «Главная/Панель», если доступна. URL — штатный
   `getDefaultUrl()` + `&app=<APP>` для модулей приложения.
2. Пункты групп фильтруются по `C` (модули) и по правам маршрута (`route.module ∈ C`;
   `parent=Settings` — только администратору).
3. Модули из `C`, не упомянутые ни в группах, ни в `hidden`, — **автоматически** в группу с
   `source.app`, равным их приложению v7; иначе в системную группу «Другие модули» в конце.
   Так новые установленные модули появляются без правки меню.
4. `hidden` убирает пункты из представления; доступ не меняется (прямой URL работает, права — Vtiger).
5. Пустые группы не выводятся. Удалённые/неизвестные модули конфигурации пропускаются без ошибок
   (в редакторе — с пометкой «нет в этой CRM»).
6. Избранное — сверху, фильтруется по `C`.
7. Системный раздел (не настраивается и не скрывается): «Предпочтения темы», «Стандартный вид»
   (если разрешён), «Настройки ModernUI» и «Настройки CRM» (администратору). Вход в настройки и
   стандартный вид всегда остаётся.
8. Подписи групп: `label[locale темы]` → `label["*"]` → системная подпись (`LBL_<APP>` для группы с
   `source.app`) → `label["en-US"]` → первый непустой вариант. Модули — перевод CRM
   (`vtranslate(label, module)`), если не задан `label` пункта. Пункт не теряется из-за отсутствия
   перевода.

Без конфигурации (`groups = null`) меню повторяет приложения v7 в порядке
`Vtiger_MenuStructure_Model::getAppMenuList()` и `vtiger_app2tab.sequence`.

**Реализовано на этапе 05** (`ModernUI_Menu_Model`; правила сборки — чистая функция `assemble()`, unit-тесты
`tests/php/MenuTest.php`):

- Кандидаты: модули приложений из `getAllVisibleModules()` (только приложения `getAppMenuList()`; строки других
  приложений — `SETTINGS`, `ANALYTICS`, пустое приложение, которое пишут установщики некоторых расширений, — меню v7 не
  показывает, такие модули обрабатываются как модули вне приложений) и модули вне видимых приложений с собственным
  экраном — «Главная» (право модуля `Dashboard`, как в `SidebarAppMenu.tpl`), `Calendar`, `Documents`, `MailManager`,
  `Reports` и entity-модули с `presence IN (0,2)`, кроме `Emails`, `Events`, `ModComments`, `Webmails`, `Users`; та же
  проверка `isAdminUser() || hasGlobalReadPermission() || hasModulePermission()`. Модуль с записями `vtiger_app2tab`,
  которые невидимы или относятся к приложению вне меню v7 (скрыт администратором в редакторе меню CRM или так записан
  установщиком), — кандидат, но скрыт, пока конфигурация явно не поставит его в группу: без настроек меню темы не
  показывает того, чего нет в меню v7 и среди собственных экранов.
- Подписи групп приложений и «Другие модули» — словари темы (RU/EN/DE: `menu.apps.*`, `LBL_MENU_APP_*`), а не язык
  CRM; группа неизвестного приложения — перевод CRM `LBL_<APP>`. Модули — перевод CRM. Значки групп по умолчанию:
  MARKETING `megaphone`, SALES `target`, INVENTORY `package`, SUPPORT `life-buoy`, PROJECT `briefcase`, TOOLS `wrench`,
  остальные `layout-grid`.
- Модуль может стоять в нескольких группах (как Contacts/Accounts в приложениях v7), один раз в группе. Новый модуль
  добавляется во все группы с `source.app` его приложений, иначе в «Другие модули» (группа `other` создаётся в конце).
- Значок пункта: шрифт `vicon-*`, изображение `layouts/v7/modules/<M>/<M>.png` или две буквы модуля с `source=custom`
  (как `getModuleIcon()`, без HTML), либо значок Lucide из настройки.
- URL — `getDefaultUrl()` модуля (проверка `^index\.php\?…`, иначе `index.php?module=<M>&view=List`) и `&app=<APP>`
  группы; маршрут — `index.php?module=…&view=…&<params>`.
- Сбой чтения модулей CRM при построении меню даёт пустое меню (системный раздел остаётся) и запись в журнал vtlib.

### 6.3. Редактор меню (этап 05)

Порядок групп и пунктов — перетаскиванием и кнопками «Выше/Ниже/В группу…»; клавиатура: фокус на
пункте, `Alt+↑/↓` — переместить, `Enter` — изменить, `Delete` — скрыть (с отменой). Подписи — поля
RU/EN/DE и «общая». Значки — выбор из набора с поиском. Список «Нет в меню» показывает доступные
модули вне конфигурации.

**Реализовано на этапе 05** (`frontend/src/settings/sections/MenuSection.vue`): перетаскивание — `vue-draggable-plus`
(групп и пунктов, между группами); те же действия — кнопками у каждой строки и клавишами на строке в фокусе (группа —
`Alt+↑/↓`). Скрытый пункт остаётся на своём месте зачёркнутым («Показать» возвращает его туда же). Разделы «Не
размещены» (появятся сами — с указанием группы) и «Скрытые из меню» (в том числе скрытые в редакторе меню CRM) с
кнопкой «Разместить». Модули конфигурации, которых нет в этой CRM, помечены «нет в этой CRM» и удаляются кнопкой.
«Добавить ссылку на представление CRM» — модуль из каталога, представление (`List`) и номер фильтра; URL ввести нельзя.
Предпросмотр справа — меню, которое сервер строит из черновика с правами текущего администратора, на выбранном языке
RU/EN/DE. В профиле роли меню либо общее, либо своё («Задать меню для роли» копирует текущее).

```json
                  "density": "standard", "fontScale": 100, "font": "inter" },
  "branding": { "logoUrl": "test/logo/…", "title": "…" },
  "menu": { "favorites": [ … ], "groups": [ { "id": "sales", "label": "Продажи", "icon": "briefcase",
            "items": [ { "id": "m:Leads", "label": "Обращения", "url": "index.php?module=Leads&view=List&app=SALES",
                         "icon": { "vicon": "vicon-leads" }, "active": false } ] } ],
            "system": [ … ] },
  "personal": { "values": { … }, "allowed": ["locale", "appearance.density", …], "revision": 3 }
}
```

Только данные текущего пользователя; id пользователя в ответе не нужен клиенту и не передаётся.
`ETag` = хэш (ревизии областей, версия схемы, mtime файла привилегий пользователя, язык,
сборка); ответ `Cache-Control: private, no-cache`.

**Реализовано на этапе 02** (`ModernUI_Client_Model`, проверка на клиенте — `frontend/src/api/guards.ts`):
`v`, `build`, `module` (версия модуля), `user`, `locale`, `theme` = `{active, reason, mode, canOptOut,
canSelfEnable, cacheKey}` (вместо числовой `revision` — `cacheKey`: хэш пользователя, ревизий областей,
версии схемы и сборки; им же загрузчик подписывает кэш токенов в `localStorage`), `appearance`,
`menu.system` (только системный раздел: `{id, url}` или `{id, action}`; ссылки — только
`index.php?…`), `personal`. `branding` и группы меню появятся с редактором (этапы 05–06). `ETag` пока —
хэш тела ответа (304 при совпадении); замер и, при необходимости, хэш из ревизий — этап 04 (Q9).
Ошибки блокирующего состояния (модуль выключен, версия Vtiger, схема) — HTTP 409 и код `MU_*`.

**Этап 05.** Добавлены `branding` = `{logoUrl, title}` (`null` — как в CRM; `logoUrl` только вида
`public.php?type=logo&key=modernui_<sha1>.png`), `menu.groups` (`{id, label, icon, items: [{id: m:<модуль>|r:<маршрут>,
module, label, url, icon}]}`), `menu.favorites`, `menu.favoritesEnabled`, `menu.compact`, `locale.default` и
`personal.inherited` — значения разрешённых ключей без личной области («как задал администратор»). Клиент проверяет
каждое поле (`frontend/src/api/guards.ts`): URL пунктов только `index.php?…`, подписи без `<>`, значки из набора,
изображения значков только из `layouts/<layout>/modules/<M>/<M>.png`. Подписи меню приходят уже на языке темы
пользователя; тело ответа (и `ETag`) различается по языку и правам.

**Этап 04.** `appearance` дополнен картой `tokens` — CSS-переменные (без префикса `--mu-`), вычисленные сервером из
действующих значений (`ModernUI_Tokens_Model`: `primary`, `primary-strong`, `primary-hover`, `primary-soft`, `bg`,
`surface`, `font-scale`, `font-family`, `row-height`, `table-head-height`, `input-height`, `button-height`,
`cell-padding`, `menu-item-height`, `icon-button`); клиент проверяет имя и шаблон значения каждого токена. Та же карта
печатается таблицей стилей `action=Tokens` (`architecture.md` §5.1). `cacheKey` теперь включает роль пользователя и
источник ролевых настроек (иначе смена роли с одинаковой ревизией документа давала бы тот же ключ) и подписывает URL
таблицы токенов; кэша токенов в `localStorage` больше нет. Личная страница предпочтений без JS получила поля
«Плотность» и «Размер текста» (если `appearance.density` / `appearance.fontScale` входят в `policy.userOverrides`, по
умолчанию — да); пустое значение «Как задал администратор» удаляет личное значение. Остальное оформление — редактор
этапа 05.

## 8. Предпросмотр, сохранение, конфликты, сброс

- **Предпросмотр**: черновик живёт в клиенте; цвета/плотность/шрифт применяются к текущей странице
  через CSS-переменные, меню — через `action=Save&mode=previewMenu` (сервер строит меню черновика с
  правами **текущего** администратора, ничего не сохраняет). Вход другим пользователем не
  имитируется; для ролевого меню показывается структура с пометкой «пункты без прав у роли будут
  скрыты». «Отменить» возвращает сохранённое состояние; уход со страницы с черновиком — запрос
  подтверждения.
- **Сохранение**: запрос содержит область, документ и `baseRevision`. Сервер валидирует,
  выполняет `UPDATE … SET revision = revision + 1 WHERE scope=? AND scope_key=? AND revision=?`.
  0 строк → `MU_CONFLICT` с текущей ревизией, автором и временем изменения: клиент предлагает
  «Загрузить актуальные», «Сравнить» или «Перезаписать» (повторный запрос с новой ревизией).
- **Сброс**: область удаляется (возврат к предыдущей по приоритету); для `global` — к значениям
  по умолчанию, `theme.mode` при этом не меняется. Пользователь сбрасывает только свои настройки.
- Изменение настроек не трогает профили, роли, `vtiger_app2tab`, языковые и форматные настройки
  пользователя CRM.

**Реализовано на этапе 05:**

- Предпросмотр оформления — `tokensFor()` черновика ставится inline на `<html>` этой страницы (вид меняется сразу и у
  самого редактора); при уходе со страницы восстанавливается сохранённое. Предпросмотр меню —
  `action=Save&mode=previewMenu` (допускаются только ключи `navigation.*`), ответ — меню и список неизвестных модулей.
- «Сохранить» отправляет **весь документ** области (`values` — плоская карта, `baseRevision`, для роли `inherit`).
  Конфликт: HTTP 409 `MU_CONFLICT` с `{revision, updatedBy: «Имя (логин)», updatedAt}`; диалог показывает, что
  изменено там (сравнение сохранённой базы черновика с текущими значениями сервера) и что в черновике, и предлагает
  «Загрузить актуальные» (черновик отбрасывается) или «Перезаписать моими» (повтор с новой ревизией). Ошибки значений —
  HTTP 400 `MU_INVALID_VALUE` с путями (до 20), поля подсвечиваются в разделах.
- «Сбросить раздел» возвращает ключи раздела к унаследованным значениям (общие — к значениям по умолчанию, роль — к
  общим) в черновике; применяется сохранением. Для общих настроек раздел «Пользователи и роли» не трогает `theme.mode`,
  `theme.pilot.users`, `theme.pilot.roles`. Профиль роли удаляется кнопкой (`mode=deleteRole` с ревизией); личные
  настройки пользователя администратор только сбрасывает (`mode=resetUser`).
- После сохранения изменений режима и пилота страница перезагружается — серверная часть (состояние, формы) показывает
  сохранённое.
- Личные предпочтения (Vue, `frontend/src/preferences/`) сохраняются вместе с ревизией личной области
  (`Preferences&mode=save&baseRevision=…`): сохранение из другой вкладки или сеанса между ними — `MU_CONFLICT` и кнопка
  «Загрузить актуальные», а не тихая перезапись. Серверная форма без JS по-прежнему сливает ключи (`update()`).
- Избранное принимается только из кандидатов меню самого пользователя (`MU_INVALID_VALUE` с путём
  `navigation.favorites[i]`): через избранное нельзя проверить существование чужих модулей.

## 9. Перенос между CRM (экспорт/импорт JSON)

```json
{
  "format": "modernui.settings",
  "formatVersion": 1,
  "exportedAt": "2026-11-01T10:00:00Z",
  "source": { "module": "1.0.0", "vtiger": "8.4.0" },
  "global": { "v": 1, "theme": { "mode": "pilot", "pilot": { "users": [ { "userName": "anna" } ],
              "roles": [ { "path": ["Organisation", "CEO", "Sales Manager"] } ] } }, … },
  "roles": [ { "role": { "path": ["Organisation", "CEO", "Sales Manager"] }, "inherit": false, "settings": { "v": 1, … } } ],
  "users": [ { "user": { "userName": "anna" }, "settings": { "v": 1, … } } ]
}
```

- Никаких числовых id: пользователи — по `user_name`, роли — по пути имён от корня (`parentrole` →
  `rolename`), модули — по имени. Логотип не экспортируется (в отчёте импорта — «загрузите логотип»).
- Экспорт: администратор выбирает части (общие, роли, личные). Личные — только ключи, разрешённые
  в `policy.userOverrides`.
- Импорт: файл ≤ 256 КБ, JSON, `format`, `formatVersion` ≤ поддерживаемой; старые версии
  поднимаются конвертерами; затем **предпросмотр** — что изменится, неизвестные модули (сохраняются,
  помечаются), неразрешённые роли/пользователи (пропускаются), невалидные значения (с путём) —
  и применение выбранных частей одной транзакцией. Существующие области, не выбранные для импорта,
  не меняются.

**Реализовано на этапе 05** (`ModernUI_Transfer_Model`, `Settings_ModernUI_Transfer_Action`; проверка на двух базах
MySQL с разными id — `tests/php/db/TransferTest.php`, в браузере — `e2e/settings.spec.ts`):

- Экспорт — `GET …&action=Transfer&mode=export&parts=global,roles,users`, вложение `modernui-settings-<время>.json`;
  `source` = `{module, vtiger, schema}`. Пилотные пользователи — `{userName}`, роли — `{path}`; пользователи и роли,
  которых больше нет, в файл не попадают. Логотип не экспортируется (`"omitted": ["branding.logo"]`). Часть «личные»
  содержит только ключи из `ModernUI_Settings_Model::userOverridableKeys()` (без `user.standardView/selfEnabled`). В
  файле нет id, ФИО, почты, паролей и записей CRM; логины — единственные данные пользователей (часть «личные»
  включается отдельно).
- Сопоставление: роль — по пути имён **ниже корня** (корень установки называется по-разному: Organisation /
  Organization / локальное имя), без учёта регистра; несколько ролей с одним путём — «неоднозначно», пропуск. Пользователь —
  по логину без учёта регистра. Неизвестные модули меню сохраняются (в другой CRM они могут быть), маршруты с
  `viewname` помечаются «проверьте фильтр».
- Предпросмотр (`mode=preview`, тело `json`) ничего не пишет и возвращает отчёт и `fingerprint` — хэш текущих ревизий
  всех затронутых областей. Применение (`mode=apply`, `parts`, `includeMode`, `fingerprint`) повторяет анализ; если
  хотя бы одна область изменилась после предпросмотра — `MU_CONFLICT`, ничего не записано. Запись — одна транзакция
  (`START TRANSACTION … COMMIT`, при ошибке `ROLLBACK`).
- `theme.mode` из файла применяется только с явной отметкой «Применить и режим нового интерфейса» (в отчёте —
  отдельной строкой «было → станет»); логотип принимающей CRM сохраняется. Общие настройки файла заменяют документ
  целиком (кроме режима и логотипа), профиль роли — целиком вместе с `inherit`, личные — заменяют разрешённые ключи,
  `user.standardView/selfEnabled` пользователя сохраняются.
- Отказы: не JSON, список, чужой `format`, лишний ключ верхнего уровня, документ без `v` — `MU_IMPORT_FORMAT` (с путём);
  `formatVersion` новее — `MU_IMPORT_VERSION`; больше 256 КБ — `MU_IMPORT_TOO_LARGE`. Невалидные и неизвестные значения
  внутри документов не отвергают файл: они перечислены в отчёте с путём и не применяются.

## 10. Lifecycle и данные

| Событие | Настройки и таблицы | Ссылки, пункт настроек |
|---|---|---|
| install | миграции; `global` с `theme.mode=off` | ссылки создаются (обработчик всё равно отдаёт `false` при `off`); пункт настроек |
| disable | без изменений | ссылки удаляются; пункт настроек остаётся, но страница сообщает «модуль выключен» |
| enable | без изменений | ссылки восстанавливаются |
| update | миграции; значения не сбрасываются | пересинхронизация |
| uninstall (по умолчанию) | **таблицы сохраняются** (переустановка восстановит настройки) | удаляются ссылки и пункт настроек |
| uninstall с «Удалить данные ModernUI» | `DROP TABLE vtiger_modernui_*`, удаление `test/logo/modernui_*`; перед этим предлагается экспорт | то же (этап 02: `ModernUI_Lifecycle_Model::$purgeOnUninstall`, на стенде — `task crm:uninstall -- --purge`; кнопка — этап 10) |
| reinstall при сохранённых таблицах | миграции до текущей версии; настройки восстановлены, но `theme.mode` принудительно `off` с уведомлением администратору | создаются заново |

Чужие данные не удаляются: ни строки ядра, ни файлы вне `test/logo/modernui_*`. Ссылок на удалённые
файлы не остаётся: uninstall удаляет их, а при удалении файлов без uninstall `Header.php` не выводит
ссылки на отсутствующие файлы.

## 11. Права настроек

- Административные view/actions — `Settings_Vtiger_*` (только `isAdminUser()`). Этап 05:
  `Settings_ModernUI_Data_Action` (GET, только чтение, Referer), `…_Save_Action` (`save`, `previewMenu`, `deleteRole`,
  `resetUser`), `…_Logo_Action` (`upload`, multipart), `…_Transfer_Action` (`export` — GET, `preview`/`apply`) — все
  наследуют `Settings_Vtiger_Basic_Action`: проверка администратора ядром, для записи POST + CSRF
  (`validateWriteAccess()`); JSON-параметры читаются `getRaw()` (без очистки текста подписей ядром) и проверяются схемой.
- Личные — любой вошедший; `scope_key` = id из сессии; ключи вне разрешённых отвергаются `MU_FORBIDDEN_KEY`.
- Ни одна настройка не расширяет права: меню строится из модулей, доступных пользователю по
  правилам Vtiger; скрытие — только представление.
- Пилот и исключения не дают доступа к данным, только выбирают оформление.

## 12. Проверяемое поведение (сводка для этапов 05 и 10)

1. После установки тема выключена у всех, включая администраторов.
2. «Включить для меня» — тема у текущего администратора, у остальных нет.
3. Пилот по роли: пользователь роли получает тему со следующей страницы; пользователь другой роли — нет.
4. «Стандартный вид» пользователя отключает тему только у него; при `allowOptOut=false` переключатель недоступен.
5. Цвет/плотность роли перекрывают общие; личный размер текста перекрывает роль только при разрешении.
6. Скрытый модуль пропадает из меню темы, но открывается по прямой ссылке при наличии прав;
   модуль без прав не появляется ни в каком меню, даже если указан в конфигурации.
7. Новый установленный модуль появляется в меню автоматически (группа его приложения или «Другие модули»).
8. Два администратора сохраняют одновременно — второй получает конфликт, данные первого не потеряны.
9. Экспорт с одной CRM и импорт в другую: роли и пользователи сопоставлены по именам, неизвестные
   показаны в отчёте, существующие настройки не испорчены.
10. Подписи групп RU/EN/DE и fallback по §6.2 п. 8; JSON сохраняет все варианты.
11. disable → enable и update сохраняют настройки; uninstall по умолчанию сохраняет таблицы.
12. `modernui=off` возвращает стандартный вид на сессию без JS.

## 13. Этап 05: интерфейс настроек (фактическое поведение, 2026-11-04)

### 13.1. Страницы

- «Настройки → ModernUI» (`index.php?module=ModernUI&parent=Settings&view=Index`): сверху редактор (Vue, entry
  `settings`), разделы **Оформление**, **Меню**, **Пользователи и роли**, **Совместимость**, **Импорт и экспорт**; под ним
  серверная часть — состояние, «Включить/выключить для меня», «Выключить для всех», безопасный режим, «Восстановить»,
  проверка интерфейса в браузере. Серверные формы пилота при работающем редакторе скрыты (тот же список в разделе
  «Пользователи и роли»). `&editor=off` — страница без редактора (все серверные формы, без Vue); ссылка на неё есть на
  странице и в разделе «Совместимость». Редактор работает и при выключенном модуле (подготовить тему до включения),
  требует актуальной схемы.
- «Предпочтения ModernUI» (`index.php?module=ModernUI&view=Preferences`): редактор личных предпочтений (entry
  `preferences`) поверх серверной формы, которая скрывается после монтирования; `&editor=off` — только форма.
- Код и словари редакторов — в отдельном chunk `editor` (`vite.config.ts`): shell на страницах CRM его не загружает.

### 13.2. Области в редакторе

Разделы «Оформление», «Меню» и «Совместимость» правят выбранную область: «Всех (общие настройки)» или профиль роли
(список ролей с отступом по иерархии, корень `H1` исключён). В профиле роли каждое значение либо «своё для роли»
(флажок), либо наследуется из общих и показано неактивным; флажок «Также для подчинённых ролей без своего профиля» —
`meta.inherit`. Смена области или уход со страницы с несохранённым черновиком требуют подтверждения. «Пользователи и
роли» и «Импорт и экспорт» — только общие настройки. Таблица профилей ролей показывает, откуда роль получает настройки
(свой профиль / профиль предка с наследованием / общие).

### 13.3. Логотип и название

- Загрузка: `POST …&action=Logo&mode=upload` (поле `logo`, ≤ 512 КБ; клиент отказывает раньше). Проверки:
  `is_uploaded_file`, `getimagesize()` → только PNG/JPEG/GIF, стороны 16–4096 px, декодирование GD
  (`imagecreatefromstring`), перекодирование в PNG с прозрачностью и уменьшением до 600×200, имя
  `modernui_<sha1 PNG>.png`, запись через временный файл и `rename()` в `test/logo/` (каталог логотипов CRM), выдача —
  штатный `public.php?type=logo&key=…`. Ни имя, ни путь клиента не используются; SVG, PHP-файл с расширением `.png`,
  повреждённое изображение — `MU_LOGO_FORMAT`; нет GD — `MU_LOGO_UNSUPPORTED`; каталог не доступен для записи —
  `MU_LOGO_STORAGE`.
- Загрузка не меняет настройки: файл попадает в черновик (`branding.logo`) и действует после «Сохранить». Файлы
  `modernui_*.png`, на которые не ссылается общий документ, удаляются через сутки (при сохранении общих настроек и при
  следующей загрузке); удаление модуля с «Удалить данные ModernUI» удаляет все такие файлы. Логотип CRM
  (`vtiger_organizationdetails`), документы и PDF не меняются.
- В шапке тема вставляет остров `brand` в ссылку логотипа v7 после её изображения; изображение v7 скрывается только
  под `html[data-mu-replaced~="logo"]` (пока остров смонтирован). Отметки расширений внутри ссылки логотипа остаются.
  Своё название выводится рядом с логотипом (многоточие, полный текст в `title`).

### 13.4. Язык темы

- Редактор настроек: выбор «Как в CRM / Русский / English / Deutsch» в шапке редактора сохраняется сразу как личный
  `locale` администратора (только если `locale` разрешён политикой); тексты меняются без перезагрузки, черновик и его
  предпросмотр остаются.
- Предпочтения: выбор языка меняет тексты редактора сразу и сохраняется вместе с остальными значениями; несохранённые
  поля не теряются. Язык и форматы профиля CRM не меняются (запись идёт только в личную область ModernUI).
- Подписи меню в `Bootstrap` и предпросмотре — на языке темы по §6.2 п. 8; предпросмотр меню переключается между
  RU/EN/DE независимо от языка редактора.

### 13.5. Кеширование

Ключ таблицы токенов (`cacheKey`) включает пользователя, роль, источник ролевых настроек, ревизии областей, схему и
сборку: смена роли пользователя (проверено e2e на чистом стенде) даёт новый URL таблицы токенов и новое меню со
следующей страницы. `Bootstrap` — `private, no-cache` с `ETag` от тела (язык, права и меню входят в тело). Кеша
настроек и меню в `localStorage` нет.
